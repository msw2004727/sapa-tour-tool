### 一張圖跟著一個行程，資料另開一份文件

v3.13 是「每天一張」，理由是怕塞爆同步流量。這次改成每個行程項目一張，同時把底圖從 `settings.dayBg` 搬到**獨立的 `photos` 文件**（`DOC_KEYS` 多一個 `photos`，結構 `photos.items[行程id] = {src, op, kb}`）。

搬家的理由跟畫面無關，是寫入成本：底圖要是留在 `itinerary` 裡，領隊每改一個字都會走 `Store.save('itinerary')` 整份覆寫，等於每次改行程名稱都要重傳所有圖片。獨立成一份文件之後，改圖走 `Store.savePath('photos','items/<id>', …)`，只送出那一張。

> v3.14 當時還有一支 `dayHeroBg(day)` 負責挑首頁「今日行程」主卡的底圖，**v3.15 已經整個移除**，見下一節。

**舊資料清理**：`applyRemote()` 裡加了一次性清除——**領隊的裝置**收到雲端快照時，若發現還有 `settings.dayBg` 就刪掉並寫回 null。只讓領隊做是避免 33 支手機同時搶著寫。（實際上線後查過正式站，`settings.dayBg` 已經是空的。）

行程被刪除時，它的底圖會一起刪掉，不會留下孤兒資料。

### 容量實測（回答「會不會爆」）

測試是把壓好的圖複製到全部 30 個行程，量最壞情況：

| 項目 | 數字 |
|---|---|
| 單張輸出尺寸 | 360×203（16:9），從 v3.13 的 420×236 縮小 |
| 單張編碼上限 | 9,000 bytes（v3.13 是 11,000） |
| 實測單張 | 約 8.7 KB WebP |
| **30 個行程全部有圖** | **352 KB**（含 base64 膨脹，整份 `photos` JSON 353 KB） |
| 目前正式站全部資料 | 18 KB（settings 2.5／itinerary 7.4／members 4／groups 1.1／notebook 2.7） |

結論：**不會爆。** 滿載後整包約 370 KB，`localStorage` 上限 5 MB 還有十倍餘裕。編輯畫面最下面會即時顯示「全團共 N 張底圖，合計約 X KB」，超過 600 KB 才會出現建議控制的字樣。

> 順帶更正我在 v3.13 講過的一句話：我當時說「根節點監聽，任何人改任何欄位整份資料庫就會重新下載到 33 支手機」——這句太悲觀。Firebase Realtime Database 第一次同步之後，後續走的是**差異推送**，改一個欄位只會傳那個欄位，不是整包重下。真正要看的成本是「每次打開 App 的初次同步」與 `localStorage` 容量，這兩項 370 KB 都在安全範圍。也就是說，v3.13 當初「怕爆所以只做每天一張」的理由本身是站不住的，這次改成每個行程一張沒有付出額外代價。

### 三個 bug 的真正原因

**（a）第一次上傳時濃度卡在 9%。** `dbgField()` 產生濃度滑桿時寫了 `(has?'':' disabled')`——`has` 是「這個行程**已經**有底圖」。第一次上傳的當下 `has` 還是 false，所以畫面上那支滑桿從一開始就是 disabled，選了照片也不會自己解鎖。修法：`dbgOpenFile()` 載入圖片成功後主動把 `disabled` 拿掉。已寫成測試（「還沒有圖時濃度是鎖住的」→「選了照片之後濃度立刻解鎖」→「第一次上傳就能指定濃度」三連檢）。

**（b）同一個行程再上傳一張像是沒有覆蓋。** 資料層其實是有覆蓋的（本機測過 base64 尾巴會變）。真正的症狀來自 `dbgApply()` 最後那行 `sheetItem(SHEET.id)`——它把**整張編輯表單重開**了。重開的表單是從資料庫重讀的，所以領隊剛剛改了一半、還沒按「儲存」的名稱或說明文字全部被沖掉，看起來就像「什麼都沒變」。修法：改成 `dbgRefresh()`，只就地更新底圖那一區（框、提示、按鈕、預覽、容量字樣），表單其他欄位一律不動。測試裡直接斷言「套用後沒存的文字沒被沖掉」。

**（c）「選照片」按鈕的 SVG 跑位。** CSS 有一條 `.f label{display:block}`，那是給欄位標題用的，但它是**後代選擇器**——`.f` 裡面那顆 `<label class="btn sm">選照片</label>` 也被打回 `display:block`，於是 `.btn` 的 `inline-flex` 置中失效，圖示往上跑 10px。修法改成直接子代 `.f>label`，並補一條 `.f>label.btn{display:inline-flex}` 當保險。修正後實測圖示與文字的垂直中心差為 0。

### 左右／上下移動

兩支滑桿的值是「**可移動範圍的百分比**」（−100 ~ +100），不是像素。`dbgLayout()` 每次都會依目前縮放算出可移動上限 `mx`／`my`，滑桿改動時換算成位移，拖曳結束後再換算回百分比寫回滑桿，兩邊永遠同步。縮放 100%（剛好蓋滿）時某一軸沒有移動空間，該支滑桿會 disabled 並顯示「—」，提示文字寫明「放大到蓋滿整格之後，左右／上下才有得移動」。

### 對比度（濃度放寬到 30% 之後重測）

| 濃度 | 淺色 標題／說明 | 深色 標題／說明 |
|---|---|---|
| 9%（預設） | 12.95 / 6.28 | 11.30 / 7.04 |
| 30%（上限） | 8.05 / 3.91 | 5.72 / 3.56 |

標題在兩種主題、兩種濃度下都遠高於 WCAG 的 4.5:1。**說明文字在濃度拉到 30% 時會掉到 3.9／3.6**，低於 4.5:1。這是給領隊的手動上限，不是預設值，但值得知道：想要圖片明顯一點時，說明那行的可讀性是會犧牲的，建議一般情況留在 15% 以內。

`audit/dbgtest.js` 重寫為每個行程一張，9 個區段共 46 項：上傳→壓縮→存檔、輸出尺寸 360×203、只有指定那張卡掛 `has-bg`（沒圖的卡不會畫出底圖）、整頁只存一份 data URI、兩種主題 × 兩種濃度的對比度實測、濃度鎖定與解鎖三連檢、覆蓋上傳不沖掉未存文字、移除後按鈕回到初始狀態、左右上下滑桿與拖曳雙向同步、30 張滿載容量、WebP 不支援時退回 JPEG。

## 二、v3.15：首頁「今日行程」不顯示底圖（2026-09-11）

小麥看過 v3.14 上線後的畫面，決定首頁那張主卡不要底圖。這一版把它整個拿掉，不是用 CSS 藏起來。

### 拿掉了什麼

| 位置 | 動作 |
|---|---|
| `04-core.js` `todayCard()` | 不再輸出 `has-bg` class 與 `<i class="cbg">` 底圖層 |
| `04-core.js` `dayHeroBg()` | 整支函式刪除（原本負責挑當天要用哪一張圖） |
| `01-style.html` | 刪掉 `.card.has-bg`、`.card>.cbg`、`.card.has-bg>*:not(.cbg)` 三條規則 |

`.stop.has-bg`（行程分頁每一站的底圖）完全不動——底圖功能本身保留，只是**首頁不再出現**。

### 為什麼要連資料一起不輸出，而不是只加一條 CSS 隱藏

首頁主卡的底圖是把整張 8.7 KB 的 data URI 寫進行內 style 的。用 CSS 藏起來的話，那串字元每次渲染首頁還是會進到 DOM，等於白白付流量與記憶體。現在首頁的 HTML 裡一個 `data:image` 都不會出現。

順帶解掉兩個原本要另外處理的糾纏：這張卡的 `::before` 本來就拿去畫頂部彩條、高亮時又會疊上金色底，三層堆在一起要靠一連串特異性規則調和；拿掉底圖之後這些規則全部不需要了。

### 已驗收

`audit/dbgtest.js` 的第 9 區段改寫成反向斷言，而且是**最強條件**——先讓 30 個行程全部都有底圖，再逐一檢查第 1～5 天的首頁：

- 每一天都沒有 `.card.has-bg`
- 每一天都沒有 `.cbg` 底圖層
- 每一天的首頁 HTML 裡 `data:image` 出現 **0 次**
- 把「今日行程」的高亮提醒打開（測試會先確認 `.hlw` 真的存在，證明這一項有效）之後，首頁仍然 0 個底圖層、0 個 data URI
- 建置後的檔案裡已無 `dayHeroBg` 與 `.card>.cbg` 殘留

`regress.js`／`zonetest.js`／`hltest.js`／`sheetfit.js` 全部重跑通過、無 JS 錯誤。另外用 390×844 截了「30 個行程全部有圖」狀態下的首頁，確認今日行程卡是乾淨的白底。

部署：GitHub commit `a84dd84`。線上實測 750hd.com：版本 3.15、首頁 `.card.has-bg` 0 個、`.cbg` 0 個、`dayHeroBg` 已不存在、`itemBg` 仍在。

## 三、v3.16：首頁「今日行程」不顯示一句話說明（2026-09-11）

小麥問：為什麼手機上的首頁行程會顯示一句話說明，電腦版不會？

### 原因：不是手機／電腦的差別，是那台裝置記住的模式不同

`todayCard()` 原本有這一段條件：

```js
(P.planMode==='detail' && x.desc ? '<span class="td-desc">'+esc(x.desc)+'</span>' : '')
```

`P.planMode` 就是**行程分頁上方那顆「重點字卡／詳細介紹」切換**，而且它存在各自手機的 `localStorage['sapa-prefs']` 裡（跟字級、主題一起）。也就是說：

- 手機那台曾經按過「詳細介紹」→ `planMode='detail'` 被記住 → **首頁的今日行程跟著多出一句話說明**
- 電腦那台停在「重點字卡」→ `planMode='simple'` → 首頁乾淨

兩台看到不一樣，不是版本不同也不是螢幕寬度的 media query，是**行程分頁的閱讀模式偷偷影響了首頁**。這是原本設計上的耦合：那顆切換的語意應該只管行程分頁，卻被拿來當首頁的顯示條件。

### 做法

首頁的今日行程**一律只顯示時間＋名稱**（加上「進行中」徽章、「取消」標記與地圖鈕），不再看 `P.planMode`。行程分頁的兩種模式完全不受影響，詳細介紹照樣能展開。

順手刪掉只有這一處在用的 `.td-desc` 樣式。

### 已驗收

`audit/dbgtest.js` 新增第 10 區段，兩種模式都測：

- 先確認那一天的行程**確實有 5 句說明**（不然測試會假通過）
- `planMode='simple'` 時首頁找不到任何一句說明
- `planMode='detail'` 時首頁**一樣**找不到（這條才是真正鎖住這次的修正）
- 首頁沒有任何 `.td-desc` 元素
- 行程分頁在詳細模式下仍有 5 筆 `.t-detail` 與 5 筆 `.t-desc`（確認沒有誤傷）
- 建置後的樣式表已無 `.td-desc` 殘留

`regress.js`／`zonetest.js`／`hltest.js`／`sheetfit.js` 全部重跑通過、無 JS 錯誤。

部署：GitHub commit `c65b940`。線上實測 750hd.com：版本 3.16，強制把 `planMode` 切成 `detail` 後首頁仍然 0 句說明、0 個 `.td-desc`。

- 深色主題橘色按鈕對比 3.3 → 改白字 5.56。
- 320px 特大字：工具格、航班列、住宿卡摘要、提示氣泡、LCD 各有溢出或裁切 → 逐一改成可換行或單欄。

## 六、v3.19：旅遊前／中／後的時間測試與修正，加上「時間模擬」（2026-09-21）

### 跑出來的問題（v3.18 的實際表現）

| # | 情境 | v3.18 顯示 | 應該是 |
|---|---|---|---|
| 1 | 出發日台灣 05:20 | 集合「還有 1 小時 10 分」 | 還有 10 分 |
| 2 | 出發日台灣 05:40（遲到 10 分） | 「還有 50 分鐘」 | 已過 10 分 |

| 4 | 第 2～5 天 | 大字卡一直是「05:30 集合 桃園機場第二航廈」 | 今天的下一站 |
| 5 | 第 5 天晚上（已回台灣） | 「明早時間請看下面『明早時程』」＋明早時程卡 | 最後一天不需要明早 |
| 6 | App 開著過夜 | 行程頁停在昨天 | 自動換到今天 |

1、2、3、7 是同一個原因：**程式把所有時間都當越南時間**，但第 1 天搭機前人還在台灣，05:30 集合是台灣時間。長輩看到「還有 1 小時」可能就慢慢來，這是這次最嚴重的問題。

### 修法

- **兩個時區**：出發日當天、不晚於最晚一班去程起飛（`settings.flights`，目前 09:00）的時間算台灣時間，其他一律越南時間。倒數和下一站都換成絕對時間比，不再用「時:分」字串比大小。大字卡在台灣時間時會標「・台灣時間」；廣播表單也寫明「出發日 09:00 以前填台灣時間」。
- **廣播過期**：集合時間過了 4 小時（跟倒數消失同一個門檻）就不再佔住大字卡，改顯示今天下一站；頂列也回到「待公布」。資料不刪。清空廣播（自由活動）現在會記今天日期，隔天自動失效。
- **最後一天**：行程結束後改寫「最後一天辛苦了，回家路上平安」，第 5 天不再出現明早時程卡。
- **過夜**：換天時行程頁自動回到今天（表單開著時會等關掉再換）。
- **「現在＋N 分」**：先算絕對時間再決定寫台灣或越南時間；出發日越南 08:01～09:00 這段兩種寫法都會被誤判（大家在飛機上），另外記 `tz` 欄位，表單再存檔也不會掉。
- **手動指定第幾天**時，下一站依「今天的時刻」判斷。

### 途中抓到的 bug：清空後新增第一位團員「顯示已儲存，其實沒存到」

Firebase 不會存空陣列。清空後的名單從雲端回來是 `{_ts,_cleared}`，連 `items` 都沒有；原本的 `members()` 在這種情況回傳一個**沒掛在資料上**的新陣列，新增團員 push 進去之後，存檔時根本不在文件裡。行程的 `items()` 也一樣。改成把空陣列掛回文件上（跟 `photoMap()` 同一種寫法）。本機測試用 `localStorage` 存 JSON、空陣列會留著，所以本機怎麼測都正常——新測試的假雲端會照 Firebase 的習慣把空的拿掉，才抓得到。

### 之後想真的做推播時（設計路線，供日後接手）

**客戶端**：原生 Web Push。`pushManager.subscribe({userVisibleOnly:true, applicationServerKey})`；`sw.js` 加 `push`、`notificationclick`、`pushsubscriptionchange`；每一則推播都必須顯示通知（iOS 靜默推播太多會被撤銷權限）。**iPhone 要 iOS 16.4 以上、而且要「加到主畫面」從主畫面圖示開啟才收得到；LINE 內建瀏覽器不支援**——長輩最容易踩到，畫面上要講清楚。

**發送端三條路**

| 做法 | 優點 | 缺點 |
|---|---|---|
| Firebase Cloud Functions（Node ＋ `web-push`） | 資料庫一改 `trip/broadcast` 就用 `onValueWritten` 觸發，幾秒內送出、不用輪詢；集合倒數、下一站用 Cloud Scheduler 每分鐘排程；官方套件不用自己實作加密；訂閱放 `pushSubs/`，現有規則的 `$other` 已全擋、Admin SDK 不受規則限制，**不用改規則** | 要升級 Blaze（信用卡）；要在自己電腦裝 Firebase CLI 部署 |
| Cloudflare Worker | 免費、免信用卡；貼一個檔案到網頁、綁 KV、加每分鐘排程 | 不能用 `web-push`（依賴 Node 的 https／crypto），要用 WebCrypto 自己實作 RFC 8291（加密）與 RFC 8292（VAPID），用 RFC 8291 附錄 A 的測試向量驗證；廣播要靠每分鐘輪詢（約 1 分鐘內到）；免費方案每次 CPU 只有 10 ms，VAPID 簽章要快取；KV 免費額度：list 每天 1000 次，所以訂閱要放單一 key |
| GitHub Actions 排程 | 不用另外的帳號 | 最快 5 分鐘一次、實際常延遲 10～30 分鐘，「集合倒數」不準，不建議 |

**這個雲端工作環境的限制**（決定驗收方式）：連不到 Cloudflare、Apple、Mozilla 的推播服務，也連不到正式的 Realtime Database；連得到 `*.googleapis.com` 與 npm。所以發送端一定要小麥在自己的帳號部署，最後用真手機驗收。

**資料模型草案**：`settings.push = {on, types:{bc,cd,next,day,morn,pre}, cdMin, nextMin, dayAt}`（管理者的總開關與情境開關，全團同步）；`settings.pushUrl`（發送服務網址，一鍵清空要保留，跟 PIN 同類）；每支手機自己的偏好與訂閱存在發送端，不放 `trip`（33 支手機每次都要下載）。

**情境規則草案**

## 十八、v3.28：行程同一天依時間自動排序（2026-09-30）

小麥的兩個要求：查「行程頁標題的『夜宿 沙壩』是不是寫死的」，以及「同一天的行程，建立時要依時間自動排序」。

### 「夜宿 ○○」不是寫死的

行程頁每一天的標題列（`src/04-core.js` 的 `VIEWS.plan`）會找「入住晚數（`nights`）文字裡含有這一天數字」的飯店，找到就顯示「夜宿 ＋飯店名稱第一個空格前的字」。所以：

- 資料來源是團務設定裡的飯店資料：**管理模式 → 團務設定 → 飯店資料 → 編輯 → 「入住晚數」**。第一團的沙壩飯店寫的是「第 1、2、3 晚」，所以第 1、2、3 天都會顯示「夜宿 沙壩」（飯店名稱是「沙壩 Pao's Sapa Leisure Hotel」，取空格前的「沙壩」）。
- 不想顯示：把那間飯店的「入住晚數」清空（或刪掉那間飯店）就沒有了。**程式沒有動**，因為它不是誤植，是資料。
- 比對是「文字裡有沒有出現這個數字」，所以「入住晚數」請寫成「第 2、3 晚」這種帶天數的字；寫日期（例如 9/24）會被當成第 2、4 天。旅程超過 9 天時，「第 10 晚」也會讓第 1 天比對到；目前沒有處理（第一團 5 天用不到），日後有長天數的團再改成逐個數字比對。

### 同一天依時間自動排序

- 新增 `sortDayByTime(all, day)`（`src/04-core.js`，緊接 `items()`）：只排那一天**有填時間**的站，而且只在它們原本佔的位置上重排，**沒填時間的站（例如「自由活動」）留在原位**；時間相同維持原本先後；`5:30` 這種沒補零的也排得對；其他天不動。
- `ACT.saveItem` 在「新增」、「改了第幾天」、「改了時間」時呼叫它，排的是存檔後落在的那一天。**只改名稱、說明、地圖、標籤時不排**——主辦人用「上移／下移」手動排的順序不會被蓋掉（手動排的站，下次有人新增或改時間才會被重排）。
- 沒填時間的新站照舊排在那天最後。
- 沒有做成可以關掉的開關：小麥要的是預設行為，且畫面上沒有地方擺（需要時再談）。
- **沒處理的**：出發日當天的台灣時間（05:30 桃園集合）與當地時間站是混在同一天，這裡是照畫面上的時鐘排（跟行程頁顯示的一致），不做時差換算；第一團的資料排起來順序是對的。

### 測試

新增 `audit/itemsort.js`（進 `npm test`）：`sortDayByTime` 本身（沒填時間留原位、同時間維持先後、5:30、只動指定那天）；實際走表單新增、新增沒填時間的、改時間、改第幾天、只改說明文字不動順序、存檔後重新整理順序還在；以及「夜宿」跟著入住晚數消失／出現。已做突變驗證：拿掉排序呼叫，6 項變紅；改成每次存檔都排，「只改說明文字不動順序」那項變紅。

## 二十一、v3.31：團員名單改成直瀑式單欄，長姓名不再被擠出畫面（2026-10-07）

**症狀**：房號分頁「尚未分配房號」那一區，右邊一欄整排被切在螢幕邊緣，只看得到左欄；名字越長越明顯（例：MS HONG/MEI ER 洪美娥）。

**原因**：`.mlist.two` 寫死 `grid-template-columns:1fr 1fr`，而 CSS Grid 的 `1fr` 其實是 `minmax(auto,1fr)`——欄寬至少要裝得下「最長的那個不換行的名字」。團員姓名是「英文護照名＋中文名」，`.mc .nm` 又是 `white-space:nowrap`，每一欄被名字撐到 300 多 px，兩欄加起來比螢幕還寬，右欄就跑出畫面外（用長名字重現：320px 時 33 張卡片全部超出，435px 時有 16 張）。fixture 的名字是「團員01」這種短名，所以回歸測試從來沒抓到。

**小麥的決定**：「我要直瀑式往下，因為這網站主要設計都是以手機為主」。所以不是把兩欄修得比較不容易爆，而是名單一律單欄、一個人一列。

| 項目 | 位置 | 做法 |
|---|---|---|
| 尚未分配房號 | `src/04-core.js` 房號頁、`src/01-style.html` | 拿掉 `two` 這個 class 與 `.mlist.two` 的兩欄規則，跟全員名單一樣用 `.mlist` 單欄 |
| 分組頁每一組 | `.grp .gm` | grid 兩欄 → flex 單欄（同樣的毛病，只是 fixture 沒長名字所以沒爆） |
| 集合點名 | `.rc` | grid 兩欄 → flex 單欄；姓名那個 span 的行內樣式改成 `.rcn` class，補上超長單字斷行 |
| 房號總表（已分配房號的那些房間卡） | `.rooms` | `repeat(auto-fill,minmax(150px,1fr))` → 單欄。390px 寬時原本排成兩欄，每張房卡裡的名字只剩約 100px，中文名被「…」切掉 |
| 姓名太長 | `.mc .nm` | 原本 `nowrap + ellipsis`，長名字的中文部分（長輩真正要認的）被「…」吃掉。改成可以換行：`white-space:normal; word-break:keep-all; overflow-wrap:anywhere`。`keep-all` 讓它只在空格換行（英文名一行、中文名一行，不會把中文名拆開），`anywhere` 是整串沒有空格時的最後防線 |

**這次沒動的**：`memberCard` 的結構、全員名單與「我是誰」表單本來就是單欄（只受益於姓名可換行）。短名字的畫面幾乎沒有差別，只是每一列變成整列寬。

**測試**：新增 `audit/namefit.js`（875 項），見 CLAUDE.md 測試表。第一版跑出一個我沒預料到的問題：集合點名的姓名 span 沒有超長單字保護，所以才有 `.rcn`。7 個突變（姓名改回不換行、分組／點名／房號總表／尚未分配房號各自改回多欄、兩處拿掉 `overflow-wrap:anywhere`）都會讓測試變紅。

**學到的**：以後在 `grid-template-columns` 裡放長度不定的文字，要用 `minmax(0,1fr)` 並讓子項 `min-width:0`；但這個專案的名單乾脆不用多欄。fixture 的假名字要偶爾換成「最壞情況」的長名字量一次。
