## 二、技術架構

- 單一 HTML 檔（約 100 KB），Vanilla JS，無框架、無外部圖示庫；字體用 Google Fonts Noto Sans TC，載不到時回退系統字。
- 資料分 7 份文件：settings／broadcast／itinerary／members／groups／rollcall／notebook；本機 localStorage 快取優先，雲端可用時 onSnapshot 即時覆蓋。
- 領隊 PIN 純前端防誤觸（同規格書），不是資安機制。
- 預覽版限制：啟用共享資料庫的 artifact 只能給同一個 claude.ai 帳號／組織的人看，30 位團員無法直接開。正式上線需自行部署（靜態主機 + Python FastAPI 小後端，或 Firebase／Supabase）。

## 七、v1.1 首頁改版（2026-09-09）

### 問題判斷
首頁原本是 9 個等重區塊（同樣白底、同樣框線、同樣粗標題），眼睛找不到「現在最重要的是哪張」。核心問題不是卡片太多，是缺少視覺層級。

### 曾評估的四個方案
0 現況｜1 全部可收合＋領隊預設｜2 視覺分層＋分段標題｜3 綜合（採用）。
另外針對分區的視覺呈現比較了五種底色做法：A 只有分隔線、B 整段包底色、C 區塊漸層、D 左側色條、**E 明度階梯（採用）**。

不採用「三個分區各給一個色相」的理由：App 的顏色已有固定語意（橘＝廣播／緊急、靛＝可點、綠＝進行中、黃＝領隊模式），再加三個色塊會讓顏色退化為裝飾；且淡色相在戶外強光與低階 Android 螢幕上常常直接消失。改用明度（亮暗）而非色相，深淺色兩種主題都穩。

### 實際做法
- 首頁分三段，各有小標題與細線：**現在 / 稍後 / 隨時查**。
- 明度階梯：`現在` 卡＝卡片底色＋浮起陰影（`--lift`）＋頂端 3px 橘→靛細色帶；`稍後` 卡＝`--soft` 沉一階、無框；`隨時查` 卡＝透明背景只留框線，標題轉灰。
- **廣播（集合時間）與今日行程固定展開、不可收合**——集合時間被收起來是團體遲到的第一大原因。
- 其餘四張（出發前準備、航班資訊、明早時程、目前住宿）可收合，**收起時標題右邊保留一行摘要**（例如航班收起仍顯示「08:20 / 09:00 起飛」、住宿顯示飯店名），避免「看不見＝不存在」。
- **自動排序＋自動收合**：出發前把航班與行前準備排在「稍後」並展開；旅途中航班自動移到「隨時查」並收起；明早時程未公布時自動收起。領隊多半不必手動調。
- **領隊可覆寫預設**：管理模式下每張可收合卡下方有黃色小條與開關，決定團員第一次看到時是展開或收起（尚未設定時顯示「（自動）」）。
- **團員自己的選擇會記住**：存在各自手機（`P.cards`）。領隊之後改預設時 `ts` 更新，團員的舊選擇失效並套用新預設。

### 資料結構
- `settings.cards = { prep|flight|morning|hotel : { o:0|1, ts:number } }`（領隊設定，雲端同步）
- `prefs.cards`（localStorage `sapa-prefs`）＝團員自己的展開／收起，帶當時的 `ts` 做比對
- CSS 新增 token：`--soft`（次要卡片底色）、`--lift`（主卡浮起陰影），三個主題區塊各定義一份

### 同時處理
- 移除所有「領隊請點右上角 🔒 輸入 PIN 進入管理模式」這類提醒團員領隊功能的文字，不再占版面。
- 記事本／勾選清單的說明簡化為「勾選只存在你自己的手機。」

### 已驗證
Playwright 實測淺色／深色 × 標準／大／特大字級：無橫向捲動、短標籤無斷行；主題三段循環正確（跟隨系統 ↔ 淺色 ↔ 深色）；收合與領隊預設覆寫行為正確。線上 https://750hd.com 已更新並確認 Firebase 仍為「已連線」。
> 注意：先前手動切過主題的手機，localStorage 仍存著 light／dark，不會自動變回「跟隨系統」，需自己再按兩下循環回去。新使用者預設就是跟隨系統。

## 十五、v2.0 通盤優化（2026-09-09）

### 背景
針對整份專案做了一次通盤 UI/UX 與架構審查（見另一份《沙壩隨身團務_優化計劃書.md》），列出 3 個 P0 bug、11 個 UX 細節、6 個架構缺口（其中 2 個標記 ⚠️ 高風險）、7 個 P2 內容項，共 27 項，分四波＋P2 全部完成並部署。這是繼 v1.0 正式上線後，第一次針對「離線掉資料」與「PIN 明文」兩個資料完整性／資安風險做架構層級的修補。

### 一、離線同步：新增操作佇列，離線修改不再被雲端蓋掉 ⚠️→✅
問題：`Store.applyRemote()` 收到雲端快照時無條件覆寫本機——纜車上沒訊號時領隊改的廣播，下山連線後會被雲端的舊快照蓋掉。
做法：
- 新增 `Store.q`（佇列）：每次寫入先進佇列，離線時累積、連線後依序 FIFO 送出，失敗自動重試（連線列 `mode` 顯示 `offline`）。
- `applyRemote` 收到雲端資料時，會先把佇列裡「還沒送出的本機修改」重新套用在雲端快照之上，而不是直接整份覆蓋。
- 每 20 秒＋`online` 事件各觸發一次 flush；佇列內容存 `localStorage`，重新整理頁面也不會遺失。
- 已用 `audit/synctest.js` 模擬離線寫入＋雲端送回舊快照＋重新連線三種情境，驗證本機修改都保住。

### 二、局部寫入：點名／分組／成員改動不再整份互蓋
問題：每次 `save('members')` 會把 33 人整份寫回，兩支手機同時改不同人時後寫的會蓋掉前一個。
做法：新增 `Store.savePath(key, path, val)`，透過 Firebase `update()` 只送出改動的那條路徑（例如 `members/items/12/room`）。已改用局部寫入的操作：點名（`rcToggle`／`rcLabel`）、分組指派與臨時標籤（`setGroup`／`mtagsOf`）、單一成員編輯（`saveMember`／`setAirline`）。

### 三、PIN 不再明文存在公開資料庫 ⚠️→✅
- PIN 改存 SHA-256 雜湊（`settings.pinHash`，純 JS 實作，已逐字元比對 Python `hashlib.sha256` 驗證正確）；比對用 `pinOK()`，領隊用舊 PIN 解鎖成功的當下會自動把明文升級成雜湊並刪除明文欄位（`pinMigrate()`），不需要領隊做任何額外操作。
- 團務設定的 PIN 欄位改成「不改就留白」，避免每次存檔都被清空。
- 新增可選的 Firebase 匿名登入方案：`config.js` 的 `auth` 設成 `'anon'`＋套用 `firebase.rules.auth.json`（`.write` 改成 `auth != null`），只有開過網頁（自動匿名登入）的裝置能寫入。步驟寫在 `README.md`「六、v2.0 之後的安全選項」。**目前預設仍是 `auth: ''`（不登入），要不要換成匿名登入由小麥自行決定並手動切換。**

## 二十一、v2.6 集合倒數支援跨日（2026-09-09）

小麥在正式站發了「05:30 機場集合」的廣播，但標頭一直顯示「集合 待公布」，沒有開始倒數。查正式站資料後確認廣播本身存檔成功（time 05:30、label 機場集合、location 桃園機場(各自航廈)），問題出在倒數的演算法。

**原因**：廣播只存 `HH:MM`，`countdown()`／`countdownShort()` 都是拿「今天的時分」相減。越南時間 17:34 減 05:30 等於 −724 分鐘，程式判定「今天早上已經過了 12 小時」，而規則是超過 4 小時（−240 分）就退回「待公布」，所以完全不會倒數。它無從得知那是 15 天後出發當天的 05:30。這套倒數原本是為旅程中「今天稍後幾點集合」設計的，沒有考慮提前預告。

**做法**（小麥選擇「廣播加上日期欄位」）：

1. **廣播新增「集合日期」欄位**：在修改廣播表單最上方，附「今天／明天／出發日 9/24」三顆快速鍵；預設值智慧帶入（出發前帶出發日、旅程中帶今天），多數情況領隊不用動它。
2. **倒數改用日期＋時間計算**：新增 `bcDate()`（決定集合是哪一天）與 `bcDiffMin()`（回傳距離集合的分鐘數，可為負、可跨日），`countdown()` 與 `countdownShort()` 都改吃這個結果。
3. **顯示格式加上「天」**：標頭 `15天`／`2天8h`（3 天內才補小時，避免 LCD 面板變長跑版）／`12h22`／`45分`；首頁大卡 `9/24（四） · 還有 14 天 11 小時`（集合日不是今天時才在前面加日期）。剩 30 分內轉警示色、時間到、已過 N 分、超過 4 小時退回待公布等規則都維持不變。
4. **舊廣播不用重存**：`bcDate()` 在廣播沒有 `date` 時會自動推斷——出發前一律當成第 1 天（出發日），旅程中／結束後當成今天。小麥現有那筆廣播因此一上線就直接開始倒數。
5. **「現在＋N 分」跨午夜會進位**：新增 `nowPlusDate()`，`ACT.bumpTime` 與表單內的 `chipTimeFromNow` 都會同步更新日期，否則 23:50 按「＋30分」會變成「已過」。

## 二十八、v3.5：廣播一鍵貼到 LINE 群組

### 為什麼不做推播

小麥先問了「領隊廣播時能不能推播給已安裝的人」。技術上不難——SW、HTTPS、PWA、Firebase 都現成，只差一台保管 VAPID 私鑰的伺服器（Cloudflare Worker 免費額度就夠，域名本來就在 Cloudflare）。真正卡住的是 iOS：需要 iOS 16.4 以上、**必須先加入主畫面**、必須使用者手動按鈕同意，送達率約 70–85%，訂閱還可能被系統悄悄取消。把漏斗算下來 33 人大概只有三分之一收得到，而領隊會以為大家都收到了——這對異地帶團是**比沒有通知更危險**的狀態。加上 9/24 出發只剩兩週、iOS 推播我這邊完全無法測，結論是先不做，改做觸及率 100% 的 LINE 群組路徑。（LINE Notify 已於 2025/3/31 停止服務，那條免費自動推播的路也沒了。）

### 做了什麼

`bcShareText()` 把目前廣播排成一段可以直接貼進 LINE 的文字：

```
📢 機場集合通知

🕒 9/24（四）05:30
📍 桃園機場(各自航廈)

⚠️ 華航第一航廈
長榮第二航廈

完整行程、房號、分組👇
https://750hd.com/
```

動作、日期星期、地點、叮嚀自動帶入。v3.6 依小麥要求把兩樣東西拿掉：**標題前面的團名**（群組裡大家都知道是哪一團，掛上去只是佔字）與**「距離現在還有 X」那一行**（群組訊息會留在對話紀錄裡，過幾分鐘那個數字就是錯的；倒數留在 App 首頁即時算就好）。`b.idle` 或沒有時間時會換成「自由活動／集合時間待公布」那一版，不會產生一則空的集合通知。網址用 `appUrl()` 取當下網域（`file://` 之類的環境退回 `https://750hd.com/`）。

`sheetShare()` 是「通知團員」彈窗：上面是排版預覽（`.share-prev`，可長按選取），下面兩顆按鈕——

| 按鈕 | 行為 |
|---|---|
| 開啟 LINE 傳送 | `https://line.me/R/msg/text/?<encodeURIComponent(文字)>`，跳進 LINE 選聊天室、文字已填好，領隊只要選群組按送出 |

兩個進入點：**存完廣播 350ms 後自動跳出**（存好就順手通知，不用記得），以及廣播卡右下角的小按鈕。

## 二十九、v3.7：卡片高亮提醒

領隊可以把首頁某幾張可收合卡片標成「這張大家要看」，團員那邊會看到金色呼吸光暈＋淡金底色＋左上角「提醒 ON」標籤。

### 這是一顆新開關，不是沿用舊的

小麥原本想直接把現有那顆「團員預設：展開／收起」當高亮開關。讀 code 後發現不行：`CARD_DEF` 裡 `prep`／`flight`／`morning` 預設都是展開，**一上線就會有三張卡同時發光**，高亮等於沒高亮；而且團員把卡片收起來後卡片還在發光但內容是空的，語意打架。所以改成獨立的 `settings.cards[id].hl`，跟 `o`（展開預設）完全分開，預設關閉。

### 狀態與規則

| 欄位 | 存在哪 | 意思 |
|---|---|---|
| `settings.cards[id].hl` | 雲端（全團同步） | 領隊開的高亮，0/1 |
| `settings.cards[id].hts` | 雲端 | 這一輪高亮的時間戳，每次「關→開」會換新的 |
| `P.cards[id].hseen` | 團員自己手機 | 他在 `hts` 這一輪把卡片收起來過 |

`cardHL(id)` 的判斷只有兩行：領隊沒開就不亮；團員的 `hseen` 等於目前 `hts` 就不亮。

規則（小麥指定）：

- **不限制張數**，要亮幾張由領隊自己決定
- **不會時間到自動熄滅**。只有兩種熄燈方式：領隊關掉（全團熄）、團員自己把卡片收起來（只有他熄）
- 領隊關掉再開一次會產生新的 `hts`，**先前收起來過的人會重新亮一次**
- 高亮**不會**動到展開／收起，兩顆開關各自獨立（可以「預設收起但高亮」）

### 版面

`.ccard` 有 `overflow:hidden`，光暈畫在卡片裡會被裁掉，所以高亮時外面多包一層 `.hlw`，光暈畫在 `.hlw::before`（`inset:-3px`）。只動 `opacity`、不動 `box-shadow` 尺寸，手機負擔最小；`prefers-reduced-motion` 下停止動畫只留金框。

底色規則寫在 `.g-later`／`.g-ref` 之後——那兩條分區樣式會覆蓋卡片底色，特異性同分時靠順序取勝。領隊那一列 `.lead-sw` 原本就是淡金 `--gold-2`，高亮時改用深一階的 `--hl-sw`，不然會跟卡片糊在一起。領隊列改成兩排（`.ls-row`），一排展開預設、一排高亮提醒。

四個新 token（淺色／深色兩套都有）：`--hl-bg`／`--hl-edge`／`--hl-glow`／`--hl-ink`／`--hl-sw`。

### 已知限制

**高亮一張當下沒有顯示在首頁的卡片，看不到效果。** 可收合卡片只有四張，而且出現時機不同：`prep`（出發前準備）只在出發前出現、`morning`（明早時程）在旅程中才進「稍後」區、`flight` 會在「稍後」與「隨時查」之間移動。領隊的開關長在卡片本身上，所以他只能對看得到的卡片操作；但出發前對 `prep` 開的高亮，旅程開始後那張卡就消失了，設定會留著但不再顯示。

## 三十二、v3.10：修掉表單在矮螢幕被壓扁的 bug

### 症狀

小麥回報「首頁卡片位置」的開關全部擠在一起：分區標題壓在卡片列上、兩張卡的開關疊在一起、整個看板糊成一團。我這邊所有測試都過，截圖也正常。

### 原因

`.sheet-b` 是 `display:flex; flex-direction:column; overflow-y:auto`。直向 flex 的子項預設 `flex-shrink:1`，平常靠 `min-height:auto` 的自動最小尺寸保護不會被壓扁——**但只要子項自己設了 `min-height`，那個自動保護就失效**。我給 `.zb`（分區框）設了 `min-height:2.4rem`，於是表單一旦高過螢幕，四個分區框全部被壓到 2.4rem，裡面的卡片列就疊在一起。

我的截圖之所以正常，是因為 Playwright 的 viewport 開了 1200–1400px 高，`max-height:92dvh` 綽綽有餘，根本沒觸發收縮。**真實手機只有 ~700px，一定會壓。**

### 修法

兩層：

1. `.sheet-b>*{flex:none}` —— 所有表單的直接子項一律不准縮，高度不夠就讓 `.sheet-b` 自己捲。這是通則，保護的不只這一個表單。
2. 看板整塊包進 `.zb-wrap`，分區標題貼著自己的框，不再被 `.sheet-b` 的 `gap:.85rem` 一個個拆開。

### 新的測試：`audit/sheetfit.js`

專門測「矮螢幕」：320×568（iPhone SE）、375×600、390×667，各兩種字級，走過 10 個表單，檢查三件事——`.sheet-b` 的每個直接子項內容高度不得超過可視高度、每個分區框不得被壓、相鄰卡片列不得重疊。

**這個測試有先驗證過抓得到 bug**：把修正拿掉重跑，立刻報出 `zb1 155>36`、`zb2 261>46` 這類訊息，跟小麥看到的畫面完全對得起來。這件事很重要——測試如果在有 bug 和沒 bug 的版本都通過，那它沒有價值。

### 教訓

**視覺測試的 viewport 高度要貼近真實手機。** 之前所有截圖都用 900–1400px 高的 viewport，等於系統性地繞過了所有「內容比螢幕高」的情境。`regress.js` 用 800px 也還是太寬鬆，而且它只檢查橫向溢出，抓不到直向壓扁。

部署：GitHub commit `73849f0`。線上實測：版本 3.10、被壓扁的區塊 0 個。

## 三十五、v3.13：行程卡片底圖（每天一張）

### 為什麼是「每天一張」而不是「每個行程一張」

同步的監聽掛在**根節點**（`db.ref(root).on('value')`），任何人改任何一個欄位，整份資料庫就會重新下載到 33 支手機；`localStorage` 快取也是整份存，上限約 5MB。每個行程一張 ≈ 30 張圖，就算每張 10KB 也是 300KB 塞進 itinerary，等於每發一次廣播全團就多下載一次。一天一張只有 5 張，實測合計 71KB，撐得住。

視覺上也比較對：同一天六張小卡各有各的底圖會很亂，共用一張反而像「這天的主題」。

### 做法（小麥選 A 整面極淡）

底圖畫在 `.stop::before`，`inset:0` + `border-radius:inherit`，**不能用 `overflow:hidden`**——「進行中」徽章是 `top:-.65rem`，會被裁掉。卡片內容統一 `z-index:1`，文字永遠在圖上面。預設濃度 9% + `grayscale(1)`，領隊可在 3–20% 之間調。

資料 URI 只輸出**一次**，掛在外層 `.day-bg` 的 CSS 變數上；不能每張卡都塞一份十幾 KB 的字串（有寫成測試）。「進行中」那張本來就有綠底，圖再疊上去會混濁，濃度自動砍成 55%。

### 上傳流程（在行程編輯表單裡）

選照片 → 16:9 裁切框（拖曳移動、滑桿縮放）→ 下面有一張縮小的行程卡即時顯示套用後的樣子 → 按「套用這一塊」。

**只存框裡看到的那一塊**：用 canvas 把可見區域畫成固定 420×236 再編碼，不存原圖也不存縮放參數。

編碼是 WebP，品質 0.6 起跳，超過 11KB 就自動降品質重壓（最低 0.32）。**舊版 Safari 的 canvas 不支援 WebP 編碼時會「默默吐出 PNG」而不是報錯**，所以要檢查回傳 blob 的真實 `type`，不符就退回 JPEG——這條有專門的測試（把 `toBlob` 攔截成永遠回 PNG，驗證真的會退回 JPEG）。

底圖是「天」的資料，所以**套用後立刻存**（`Store.savePath('settings','dayBg/N',…)`），不跟著表單的「儲存」按鈕走，免得領隊改完圖又按取消結果圖也不見。
